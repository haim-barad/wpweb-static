# mu-plugins

Single-file WordPress **must-use plugins** deployed to client sites. Each file here drops
straight into a site's `wp-content/mu-plugins/` directory — no activation step, and it cannot
be switched off from the admin UI, which is the point for guards that must always run.

Only the plugin source lives in this repo. Hostnames, account identifiers, server paths and
credentials do not; see `scripts/hostinger-origin-monitor.config.example` for the pattern used
when a script genuinely needs environment-specific values.

## Deploying

Copy the file into the target site's mu-plugins directory and confirm it parses:

```bash
php -l wp-content/mu-plugins/<file>.php
wp eval 'echo function_exists("<a function from the file>") ? "loaded" : "NOT LOADED";' --allow-root
```

Then purge the page cache — these sites run LiteSpeed Cache, so schema and head output stay
cached until you do:

```bash
wp litespeed-purge all --allow-root
```

## Contents

### `aardvark-video-schema-guard.php`

Deployed to: **aardvarkisrael.com**

Stops incomplete `VideoObject` nodes from reaching Google.

Rank Math Pro's video module auto-detects embedded videos and writes one
`rank_math_schema_VideoObject` post-meta record per video — storing **template variables rather
than literal values**:

```
name         = %seo_title%
description  = %seo_description%
thumbnailUrl = %post_thumbnail%
uploadDate   = %date(Y-m-dTH:i:sP)%
```

If the post has no meta description, `%seo_description%` resolves to an empty string and Rank
Math omits the key entirely. Same for `%post_thumbnail%` when the post has no featured image.
Search Console then reports `Missing field "description"` or a critical `thumbnailUrl` error.

The failure is hard to spot because **the database looks healthy** — the meta is non-empty, it
just holds an unresolved token. You cannot find these by searching post meta for blank
descriptions; you have to inspect the rendered JSON-LD.

This plugin hooks `rank_math/json_ld` at priority 99 and drops any `VideoObject` missing
`name`, `description`, `thumbnailUrl` or `uploadDate`, or still holding a literal `%var%`.
Dropping is safe: nothing in Rank Math's graph back-references a `VideoObject` by `@id` (the
relationship runs outward via `isPartOf`/`publisher`), so removal leaves no dangling reference.

It is a **backstop, not the fix** — the underlying records still need real values. It matters
because Rank Math regenerates any record whose `metadata.isAutoGenerated` is `true`
(`modules/schema/video/class-parser.php`), so a corrected record must also have that flag
cleared or the next post save reverts it.

### `aardvark-sitemap-canonical-exclude.php`

Deployed to: **aardvarkisrael.com**

Keeps a page out of the XML sitemap when it declares a different canonical. Submitting a
non-canonical URL in a sitemap is a contradictory signal — the sitemap asks Google to index the
URL while the page's own head points somewhere else.

Rank Math already implements this
(`modules/sitemap/providers/class-post-type.php` → `maybe_update_query_to_exclude_posts_with_canonical_urls`)
but gates it behind a filter that **defaults to `false`**. This plugin turns it on. It applies to
every page with a custom canonical, so check the blast radius before deploying it elsewhere:

```bash
wp eval 'global $wpdb; echo $wpdb->get_var("SELECT COUNT(*) FROM {$wpdb->postmeta} WHERE meta_key=\"rank_math_canonical_url\" AND meta_value != \"\"");' --allow-root
```

The hook is spelled `rank_math/sitemap/exlude_posts_with_canonical_urls` — **"exlude" is Rank
Math's own typo**. Correcting the spelling silently disables the filter.

Note this affects the post-type sitemaps only. The Pro video-sitemap module uses a separate
provider that does not consult this filter, so a canonicalised page with video schema still
appears there.

## Gotcha: Rank Math caches sitemaps as files, not just transients

`modules/sitemap/class-cache.php` has a `file` mode that writes generated sitemaps to
`wp-content/uploads/rank-math/rank_math_<hash>.xml`. **Deleting transients does not clear these**,
and a stale file is served ahead of regeneration — this site was serving month-old sitemaps.
Clearing LiteSpeed and Cloudflare does not help either, because the staleness is at the origin.

Flush it properly after any change that should alter a sitemap:

```bash
wp eval 'RankMath\Sitemap\Cache::invalidate_storage();' --allow-root
```

Verify against the **origin**, bypassing Cloudflare, or you will just re-read an edge-cached copy:

```bash
curl -sS --resolve <domain>:443:<origin-ip> https://<domain>/page-sitemap.xml | grep -c '<loc>'
```
